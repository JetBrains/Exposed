# CRUD operations

<link-summary>Learn how to perform SQL CRUD operations using Exposed's DAO (Data Access Object) API.</link-summary>

<tldr>

**Required dependencies**: `org.jetbrains.exposed:exposed-dao` (JDBC) or `org.jetbrains.exposed:exposed-dao-r2dbc` (R2DBC)

<include from="lib.topic" element-id="jdbc-supported"/>
<include from="lib.topic" element-id="r2dbc-limited-support"/>

**Code examples**: [`exposed-dao`](https://github.com/JetBrains/Exposed/tree/main/documentation-website/Writerside/snippets/exposed-dao/),
[`exposed-dao-r2dbc`](https://github.com/JetBrains/Exposed/tree/main/documentation-website/Writerside/snippets/exposed-dao-r2dbc/)

</tldr>

CRUD (Create, Read, Update, Delete) are the four basic operations supported by any database. This section demonstrates how
to perform SQL CRUD operations using Exposed's DAO (Data Access Object) API.

These operations can be performed directly through the methods and properties of the
[`EntityClass`](https://jetbrains.github.io/Exposed/api/exposed-dao/org.jetbrains.exposed.v1.dao/-entity-class/index.html)
associated with the table. For more information, see [Entity definition](dao-entity-definition.md).

### Defer an insert

<primary-label ref="r2dbc" />

With R2DBC, you can use the [`.new()`](https://jetbrains.github.io/Exposed/api/exposed-dao-r2dbc/org.jetbrains.exposed.v1.dao.r2dbc/-entity-class/new.html)
function to schedule an insert in the entity cache and return the entity without issuing an `INSERT` statement:

```kotlin
```
{src="exposed-dao-r2dbc/src/main/kotlin/org/example/examples/CreateExamples.kt" include-symbol="scheduledMovie"}

You can then use the returned entity to read and write its columns and as the target of a reference. However, the row
has not yet been inserted, so the entity usually does not have an ID. Accessing `scheduledMovie.id.value` throws an error,
and the `findById()` function cannot find the entity until the insert is flushed.

The insert is flushed when you explicitly call the `flushCache()` function, when another statement is executed in the same
transaction, or when the transaction is committed.

When creating multiple entities, pending inserts for the same table are sent as a single batch. This makes the `.new()`
function the most efficient option for [batching inserts](#batch-inserts).

### Batch inserts {id="batch-inserts"}

<primary-label ref="r2dbc" />

Because R2DBC's `.new()` function defers the insert, you can create multiple entities and flush them together. Pending
inserts for the same table are sent as a single batch:

```kotlin
```
{src="exposed-dao-r2dbc/src/main/kotlin/org/example/examples/CreateExamples.kt" include-symbol="batchInsert"}

The `flushCache()` function explicitly controls when the pending inserts are sent to the database. Pending inserts are also
flushed before another statement is executed in the transaction and when the transaction is committed.

To keep inserts in the same batch, avoid executing another database statement between creating the entities.
Another `.new()` function adds to the pending batch, while `.newSuspend()` flushes the pending inserts before returning
and therefore starts a new batch.

> Discarding the entity does not cancel its scheduled insert. To remove an entity before the insert is
> flushed, use the `Entity.delete()` function. This removes the scheduled insert without issuing a database statement.
>

### Sort results

* With JDBC, the `.all()` function returns a [`SizedIterable`](https://jetbrains.github.io/Exposed/api/exposed-jdbc/org.jetbrains.exposed.v1.jdbc/-sized-iterable/index.html)
  which implements Kotlin's `Iterable` interface. This allows you to call any sorting methods from the [Kotlin standard library](https://kotlinlang.org/api/core/kotlin-stdlib/)
  directly.

  that extends `kotlinx.coroutines.flow.Flow`. This requires you to collect the results into a collection before using
  any sorting operators.

### Update an entity in a later transaction {id="update-later"}

<primary-label ref="r2dbc"/>

If you update an entity in a transaction other than the one in which it was created or loaded, the entity must be
attached to the new transaction before you modify it.

With JDBC, when you first update an entity in a new transaction, the DAO automatically re-registers the entity into the
new transaction's cache. It does this by first checking whether the entity is already cached, then when it is not found,
it queries the database for the most accurate row data representing the entity.

With R2DBC, property delegate setters cannot suspend, so the entity is not re-registered into the new transaction's cache.
You must manually request this behavior using the `attach()` function:

```kotlin
```
{src="exposed-dao-r2dbc/src/main/kotlin/org/example/examples/UpdateExamples.kt" include-lines="35-45"}

If the corresponding row no longer exist, the `attach()` function throws `EntityNotFoundException`.

If the transaction already caches a different entity instance for the same row and that instance has unflushed
changes, `attach()` throws `IllegalStateException`.

To deliberately discard the existing changes and attach the specified entity, use `attach(movie, force = true)`.

Suppose that you need all your table objects to have at minimum two columns for storing the date and time when a record is
created and modified. You could define a `BaseTable` to automatically handle registering these columns to any table that

Whenever a new entity is instantiated, the `created` column will be filled with the database default defined by
[`CurrentDateTime`](https://jetbrains.github.io/Exposed/api/exposed-kotlin-datetime/org.jetbrains.exposed.v1.datetime/-current-date-time/index.html),
while the `modified` column will be filled with a null value.

An entity lifecycle interceptor,
[`EntityHook`](https://jetbrains.github.io/Exposed/api/exposed-dao/org.jetbrains.exposed.v1.dao/-entity-hook/index.html),
can then be subscribed to in order to automatically populate the `modified` field whenever an existing entity is later
updated:

```kotlin
```
{src="exposed-dao/src/main/kotlin/org/example/entities/BaseEntityClass.kt"}

The example above invokes `EntityHook.subscribe()` in an abstract `BaseEntityClass` that can be used as a companion object
for any `BaseEntity` implementation, but the interceptor could be subscribed to (and unsubscribed from) on the transaction
level as well.

The subscription only performs an action when a record is updated (detected by `EntityChangeType.Updated`).

> Other actions could be detected for when an entity is created (`EntityChangeType.Created`) or removed
> (`EntityChangeType.Removed`).
>
{style="tip"}

When an update occurs, the `modified` column is populated with the current UTC time using the `nowUTC()` method. However,
the update only happens if the `modified` field has not already been set. This is checked by using `Entity.writeValues`,
which holds the column-value mappings for an entity instance before being flushed to the database. Performing this check
ensures that filling the `modified` column does not trigger the interceptor itself.

Additionally, every change (creation, update, or deletion) is logged using the
[`exposedLogger`](https://jetbrains.github.io/Exposed/api/exposed-core/org.jetbrains.exposed.v1.core/exposed-logger.html).

> For more details about using statement interceptors, see
> [DSL Statement Interceptors](Statement-Interceptors.md).
>
